# 性能与 SQLite 验收报告

## 测试环境

- 日期：2026-07-16
- 系统：Windows 11 10.0.22635，32 个逻辑处理器
- Python：3.14.0rc2
- SQLite：3.50.4
- 应用：Flask/Jinja2/SQLAlchemy，单机本地 SQLite 和本地静态资源
- 固定数据：300 篇文章、60 个项目、200 条动态、100 个公开友链、200 条公开留言及个人资料数据
- 页面测量：每页 35 次测试客户端请求，报告中位数和第 95 百分位；微基准用于比较同一机器同一数据集，不等同于公网端到端延迟

- 生产/测试静态资源：`public, max-age=31536000, immutable`，URL 带应用版本。
- 开发静态资源：`no-cache`，保证修改后可重新验证。
- 媒体：一年缓存、ETag、304 条件请求，合法媒体读取为零 SQL 查询。
- Atom/站点地图：5 分钟公共缓存并支持 ETag。

## 并发、WAL 与备份

在固定数据库副本上同时运行 8 个读取工作线程和 4 个写入线程：

- 读取：800 次，写入：320 次；总耗时 8.088 秒，读取吞吐 98.9 req/s。
- 写入每次为短事务并提交，连接繁忙超时为 5 秒。
- 竞争期间读取 P50 64.28 ms、P95 153.57 ms。
- 读取和写入错误均为 0，没有 `database is locked`。
- 被动检查点结果：`busy=0, wal_pages=1738, checkpointed_pages=1738`，全部 WAL 页已写回。
- 压力产生的 WAL 为 7,160,592 B；低流量执行截断检查点后 WAL 文件被清空/移除。
- 联合数据库与媒体备份为 86,654 B，耗时 66.25 ms；备份前后完整性检查均为 `ok`。

SQLite 的边界仍是单机、读多写少、单写入者。当前结果证明约定负载内锁等待和检查点可控，不代表适合多机或持续高并发写入。
