# 架构决策记录

## ADR-001：使用Flask模块化单体

- 状态：已接受
- 决策：使用Flask应用工厂、Blueprint、服务层和查询层构建单体应用。
- 原因：适合个人网站规模，部署简单，前后台可以共享模型、权限和模板系统。
- 影响：不拆分微服务；模块边界通过代码结构和测试维护。

## ADR-002：使用Jinja2服务端渲染

- 状态：已接受
- 决策：公开页面和后台以Jinja2输出完整HTML，原生JavaScript渐进增强。
- 原因：首屏轻量、SEO友好、兼容性高，并减少前端依赖和构建复杂度。
- 影响：交互组件优先使用服务端表单和小型脚本，不建设独立SPA。

## ADR-003：使用SQLite本地数据库

- 状态：已接受
- 决策：SQLite作为唯一业务数据库，启用外键、WAL、繁忙超时、索引和短事务策略。
- 原因：单站点部署简单、数据自主、备份方便，适合读多写少的个人网站。
- 影响：不支持多机共享写入；持续高并发写入需要未来迁移数据库。

## ADR-004：所有运行依赖本地化

- 状态：已接受
- 决策：Python包安装到本地虚拟环境；字体、图标、脚本、样式、媒体和搜索全部本地运行。
- 原因：网站不受外部CDN、云存储或远程服务可用性影响。
- 影响：需要维护依赖锁、wheel清单、许可证、静态版本和本地磁盘容量。

## ADR-005：本地媒体文件系统

- 状态：已接受
- 决策：媒体保存于实例目录，SQLite保存元数据与相对路径，Pillow生成本地缩略图。
- 原因：满足全本地约束，部署和备份边界明确。
- 影响：数据库和媒体必须联合备份；多机媒体同步不在当前范围。

## ADR-006：公开访客不注册

- 状态：已接受（可配置调整）
- 决策：首发不开放公开账号注册，后台账号由管理员创建。
- 原因：减少安全、隐私与账户维护成本，同时保留匿名评论、留言和友链申请。
- 影响：首发没有访客个人中心、社交关系或私密订阅。

## ADR-007：互动内容审核后公开

- 状态：已接受
- 决策：匿名评论、留言和友链申请经过服务端校验并根据规则进入审核。
- 原因：控制垃圾内容和恶意链接，保护个人站点维护成本。
- 影响：后台必须提供统一待审核入口、批量操作与审计记录。

## ADR-008：单机部署优先

- 状态：已接受
- 决策：应用、SQLite和媒体位于同一主机；Windows使用Waitress，Linux使用Gunicorn。
- 原因：符合SQLite与本地依赖边界，运维简单。
- 影响：反向代理为本地可选组件；不使用网络共享SQLite或多机写入。

## ADR-009：首发版本功能完整但不扩张平台能力

- 状态：已接受
- 决策：首发包含博客、个人内容、项目、动态、相册、友链、评论、留言和对应后台；暂缓公开注册、支付、聊天、多语言和插件市场。
- 原因：优先完成前后台闭环和质量指标，避免第一版失控。
- 影响：扩展点保留在数据和模块边界中，但不提前实现未使用的抽象。
