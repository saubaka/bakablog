# Flask 系统架构

## 1. 架构概览

采用模块化单体架构。一个Flask应用同时提供公开站点、管理后台、表单接口、少量JSON接口和本地运维命令，共用SQLite数据库与本地媒体目录。

```text
浏览器
  ├─ 公开页面：Jinja2 HTML + 本地 CSS/JS
  └─ 管理后台：Jinja2 HTML + 局部渐进增强
              ↓
本地反向代理（可选：HTTPS、压缩、静态文件）
              ↓
WSGI 服务（Windows: Waitress / Linux: Gunicorn）
              ↓
Flask 应用工厂
  ├─ Public / Blog / Portfolio / Interaction Blueprints
  ├─ Auth / Admin / API Blueprints
  ├─ Services：业务规则、缓存失效、图片处理
  ├─ Repositories/Queries：复杂数据查询
  └─ CLI：初始化、备份、索引、检查、维护
              ↓
  ├─ SQLite（本地磁盘）
  ├─ Uploads（本地磁盘）
  ├─ Cache（进程内或本地文件，可丢弃）
  └─ Logs / Backups（本地磁盘）
```

## 2. 分层职责

### 2.1 路由层

- 接收URL、查询参数和表单。
- 执行身份、权限和CSRF入口检查。
- 调用服务层并选择模板、重定向或JSON响应。
- 不直接编写复杂查询、图片处理或跨模型业务规则。

### 2.2 表单与Schema层

- 统一字段类型、长度、格式和跨字段验证。
- 对后台表单、访客提交和JSON接口分别定义输入边界。
- 错误信息可直接映射到可访问的表单提示。

### 2.3 服务层

- 处理文章发布、版本保存、审核、媒体引用和首页配置等业务。
- 定义事务边界，事务保持短小。
- 成功提交后执行缓存失效、搜索索引更新和审计记录。
- 图片处理等耗时操作尽可能在写事务外完成。

### 2.4 查询层

- 集中列表、详情、归档、搜索和仪表盘查询。
- 统一分页、预加载、字段选择和排序规则。
- 对热点查询记录查询计划并维护必要索引。

### 2.5 模板与静态层

- Jinja2基础布局负责元信息、导航、消息、主体和页脚插槽。
- 宏用于表单、分页、卡片、图片、标签和后台表格等重复结构。
- CSS使用设计变量、组件层和页面层组织。
- JavaScript按功能拆分为小模块，通过`defer`加载；无全站大型运行时。

## 3. Blueprint划分

| Blueprint | URL前缀 | 职责 |
| --- | --- | --- |
| `public` | `/` | 首页、关于、独立页面、站点级内容 |
| `blog` | `/blog` | 文章、分类、标签、归档、RSS |
| `portfolio` | `/projects` | 项目列表与详情 |
| `moments` | `/moments` | 动态列表与详情 |
| `gallery` | `/gallery` | 相册与照片 |
| `links` | `/links` | 友链与申请 |
| `interaction` | `/interactions` | 评论、留言、点赞等写入入口 |
| `search` | `/search` | 本地全文搜索 |
| `auth` | `/auth` | 管理账号登录、退出和会话 |
| `admin` | `/admin` | 后台所有管理页面 |
| `api` | `/api/v1` | 必要的局部异步接口，不替代服务端页面 |

后台内部可继续按内容、互动、媒体、外观和系统拆分子模块。

## 4. 请求生命周期

### 4.1 公开读取

1. 请求进入WSGI服务和Flask应用。
2. 生成或读取请求ID，加载站点基础配置。
3. 检查页面缓存或执行只读查询。
4. Jinja2渲染完整HTML。
5. 添加安全、缓存、ETag和压缩相关响应头。
6. 浏览器加载本地静态资源并执行渐进增强。

### 4.2 后台写入

1. 验证登录、角色、权限与CSRF。
2. 校验表单或JSON输入。
3. 服务层开启短事务并写入数据、版本和审计信息。
4. 提交事务；失败则回滚并返回可理解错误。
5. 提交成功后失效关联页面缓存并更新搜索数据。
6. 使用POST/Redirect/GET避免重复提交。

## 5. SQLite设计

### 5.1 连接配置

每个数据库连接都应验证以下PRAGMA实际生效：

- `foreign_keys = ON`
- `journal_mode = WAL`
- `busy_timeout`设置合理等待时间
- `synchronous = NORMAL`作为默认性能/可靠性平衡，允许生产环境提高等级

不得只在初始化连接上设置一次后假设所有连接继承。

### 5.2 并发边界

- SQLite允许多个读取者，但同一时刻只有一个写入者。
- 请求事务内不执行图片缩放、外部等待或大量循环。
- 后台批量操作分批提交，并限制并发入口。
- 定时维护、备份和友链检查通过本地CLI串行执行。
- 多个WSGI进程可以读取同一数据库，但进程数需通过锁等待和负载测试确定。
- 数据库文件必须位于本地可靠磁盘，不能放在网络共享盘。

### 5.3 查询和索引

- 所有公开列表强制分页。
- 常用组合条件围绕`status`、`published_at`、`slug`、`category_id`、`sort_order`设计索引。
- 多对多关联表使用唯一约束与双向必要索引。
- 详情页预加载分类、标签、作者和必要媒体，避免N+1。
- 搜索优先使用FTS5虚拟表，并提供无FTS5时的普通查询降级。

## 6. 缓存架构

缓存只用于可重建数据：

- 站点设置、导航、首页模块和热门公开页面可使用短TTL进程内缓存。
- 可选本地文件缓存用于跨进程共享的公开片段，但必须原子写入。
- 内容发布、修改、删除和设置更新后按命名空间精确失效。
- 登录状态、权限、草稿、审核状态等敏感数据不使用不可靠页面缓存。
- SQLite始终是业务数据真相来源，删除缓存不应影响正确性。

## 7. 本地媒体架构

- `instance/uploads`保存上传文件，按类型和年月或内容哈希分目录。
- 文件使用随机ID或内容哈希命名，扩展名由服务端检测结果生成。
- Pillow在事务外生成多尺寸图片，数据库保存宽高、格式、大小和相对路径。
- 静态模板资源与用户上传资源使用不同URL和安全策略。
- 上传目录禁止执行脚本，不允许通过路径遍历访问目录外文件。

## 8. 安全架构

- 使用Flask-Login维护后台会话，登录后轮换会话标识。
- 使用Flask-WTF/CSRFProtect保护状态变更请求。
- 密码采用成熟库提供的强哈希，不自行实现算法。
- 权限在服务端路由和服务入口检查，前端隐藏按钮不是权限控制。
- Markdown和富文本转换后使用允许列表清理HTML。
- 使用安全响应头、同源Cookie策略、上传白名单和速率限制。
- 数据库、实例配置、日志和备份没有公开静态路由。

## 9. 可观测与错误处理

- 每个请求具有请求ID、状态码、耗时和必要上下文日志。
- 认证失败、权限拒绝、审核、删除、备份等关键行为进入审计日志。
- 公开错误页不暴露堆栈、SQL、文件路径或密钥。
- 开发环境提供详细错误；生产环境写入本地轮转日志。
- 仪表盘只展示摘要，敏感日志仅授权管理员查看。

## 10. 测试边界

- 单元测试：服务层规则、表单校验、权限和工具函数。
- 集成测试：Flask测试客户端、SQLite临时数据库、上传和迁移。
- 端到端核心流程：登录、发布、搜索、审核、备份恢复。
- 性能测试：首页、列表、文章详情、后台保存和并发读写边界。
- 离线测试：阻断网络后验证所有页面与静态资源无远程依赖。
